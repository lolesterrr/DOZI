# Architecture — Dozi

## 1. Stack and why

| Layer | Choice | Why |
|---|---|---|
| App framework | **Expo (latest stable SDK) + Expo Router + TypeScript strict** | One codebase (Android now; iOS/web later); file-based routing; EAS cloud builds so no Android Studio is needed. |
| Builds | **EAS Build**: `development`, `preview`, `production` profiles | The dev client is required for native modules; `preview` gives an APK to share with testers. |
| Local database | **expo-sqlite + Drizzle ORM** | Typed schema, migrations, live queries. SQLite FTS5 for full-text search. |
| Backend | **Supabase** (Postgres, RLS, Auth, Storage, Edge Functions, Realtime) | Relational data fits drugs ↔ classes ↔ cards ↔ questions. No servers to manage; cheap to start. |
| Styling | **NativeWind** + tokens in `src/theme` | Tailwind classes are fast to write and easy for Claude Code to keep consistent. |
| Animation | **react-native-reanimated**; **Rive** for the mascot later | Smooth on low-end devices (runs on the UI thread). |
| Lists | **@shopify/flash-list** | Fast long lists on cheap phones. |
| Drawing | **@shopify/react-native-skia** | Image annotation, image-occlusion masks, roadmap path art. |
| Rich text | **@10play/tentap-editor** (TipTap in a WebView) | A mature editor: tables, lists, images, custom blocks. Stores ProseMirror JSON. |
| SRS | **ts-fsrs** | A maintained reference implementation of FSRS. |
| State | Drizzle `useLiveQuery` (local data) · **Zustand** (UI) · **TanStack Query** (network) | Each tool for one job. |
| Forms / validation | **react-hook-form + zod** | zod schemas are shared across forms, content import and sync. |
| Media | expo-image-picker, expo-image-manipulator, expo-file-system, **expo-image** | Capture, compress, store and display with caching. |
| Other Expo modules | expo-notifications, expo-haptics, expo-crypto, expo-print, expo-sharing, expo-speech, expo-font | Local notifications, feedback, IDs, PDF export, sharing, TTS. |
| Maths rendering (Phase 5) | KaTeX inside react-native-webview | PK equations. |
| Dates | date-fns + date-fns-tz | Study-day logic in `Africa/Kampala`. |
| Testing | Jest + RNTL (unit/component); **Maestro** (E2E flows) | Maestro flows are YAML, which is easy to read. |
| Monitoring (Phase 8) | @sentry/react-native, posthog-react-native | Crash reports; privacy-respecting product analytics (opt-out). |
| AI (Phase 7) | Claude API through a Supabase Edge Function, **pgvector** for retrieval | The key stays server-side; answers are grounded in reviewed content. |
| Payments (Phase 8) | Flutterwave or Pesapal (mobile money) through an Edge Function + webhook | MTN MoMo and Airtel Money support. |

Always check the current docs of each library before using it; APIs change between Expo SDKs.

## 3. Data model

### 3.1 Conventions
- **Syncable user tables** have the columns `id TEXT PK (uuid)`, `owner_id TEXT`, `created_at`,
  `updated_at`, `deleted_at NULL`, and the local-only columns `_dirty INTEGER DEFAULT 1` and
  `_synced_at TEXT NULL`.
- **Official content tables** are read-only on the device, are replaced by content-pack
  import, and carry `pack_version`.
- **Rich fields** (`*_json`) hold ProseMirror JSON. A matching `*_text` column holds the plain
  text for FTS and previews.
- JSON columns are typed with zod schemas in `src/features/<x>/types.ts`.

### 3.2 Local profile & settings
```
profiles(id, display_name, year_of_study, semester, cohort_code, timezone DEFAULT 'Africa/Kampala',
         daily_goal_xp, reminder_time, role DEFAULT 'student',  -- student | reviewer | admin
         auth_user_id NULL, created_at, updated_at)
settings(key PK, value_json)                         -- local-only UI prefs
exam_dates(id, owner_id, course_unit_id NULL, title, date, …sync cols)
```
On first launch a local profile is created with a random UUID. **Adopting local data** on first
sign-in means setting `owner_id = auth user id` on every local row, marking all rows dirty and
then syncing.

### 3.3 Personal content

comment, status, resolution, created_at)`.

## 4. Sync design (Phase 3)

**Model:** offline-first, row-level **last-write-wins (LWW)** on `updated_at`, with soft
deletes.

- **Server side (Postgres):**
  - Every synced table mirrors the local columns (minus `_dirty`/`_synced_at`) and adds
    `server_updated_at timestamptz` set by a trigger to `now()` on insert/update.
  - A `BEFORE UPDATE` trigger keeps the existing row if `NEW.updated_at < OLD.updated_at`
    (stale write → ignored).
  - RLS: `owner_id = auth.uid()` for all operations. Shared/public rows get an extra `SELECT`
    policy (Phase 6).
- **Push:** for each table in dependency order (folders → tags → media → notes → decks → cards
  → card_instances → questions → quizzes → quiz_questions → attempts → responses → review_logs
  → card_state → xp_events → streak_state → achievements → roadmap_progress → plan_items →
  exam_dates), select rows where `_dirty = 1` and upsert them in batches of 200. On success, set
  `_dirty = 0`, `_synced_at = now`.
- **Pull:** for each table, fetch rows where `server_updated_at > cursor[table]`, page by 500,
  and upsert them locally **without** marking them dirty, unless the local row is dirty and newer.
  Store the cursor per table in `settings`.
- **Card state conflicts:** `review_logs` is append-only. After a pull that brought new review
  logs for a card instance, **replay its full log history through FSRS** to rebuild `card_state`.
  This keeps reviews made on two devices while offline correct.
- **Streak/XP:** `xp_events` is append-only. After a pull, recompute `streak_state` from the
  events plus freeze/repair usage.
- **Triggers:** sync runs on app start, when the app returns to the foreground, when the network
  reconnects, after a session ends (debounced 10 s) and manually from the Me tab. It uses
  exponential backoff on errors.
- The UI never waits for sync. A small status indicator shows synced / syncing / offline /
  error.
- `sync/logic.ts` (merge decisions, ordering, replay) must be unit-tested with in-memory SQLite.

## 5. Media pipeline

1. Pick or capture with expo-image-picker.
2. Compress with expo-image-manipulator: long edge ≤ 1600 px, JPEG 0.7 (≈ 150–350 KB).
3. Save to `FileSystem.documentDirectory + 'media/<id>.jpg'` and insert a `media` row
   (`upload_status = 'local'`, or `'queued'` if the user is signed in).
4. Rich content references images as `media://<id>`. The `<MediaImage id>` component resolves
   the local file first, otherwise downloads from Supabase Storage via a signed URL and caches it.
5. The upload queue runs only when sync is enabled, respecting "Wi-Fi only". Storage path:
   `user-media/<owner_id>/<media_id>.jpg`, with Storage RLS on the first folder segment.
6. **Annotation** saves the strokes as `annotation_json` on a new media row that has
   `derived_from = original`. A flattened JPEG is also rendered with Skia for display and
   export.
7. **Cleanup:** a weekly job deletes local files with no referencing row. Settings shows the
   storage used.

## 6. Content pipeline (Phase 4)

```
content/*.yaml ──content:validate──▶ zod OK? ──content:push──▶ Supabase (status=draft/in_review)
                                                          │
                                   Reviewer Mode in app ◀─┘ approve / request changes
                                                          │
                              status=published ──content:build──▶ packs/<unit>/<version>.json.gz
                                                          │                → Storage (public)
                                                          ▼                → content_manifest row
                                  App: check manifest → download (size shown) → verify checksum
                                       → import in one transaction → content_packs.version++
```
- One pack per course unit. Each pack contains every published official row for that unit.
- A small **starter pack** (the first topics of the student's likely course unit) is bundled
  in `assets/starter-pack/` so the roadmap works on first launch with no data.
- `content:push` and `content:build` run on the developer's computer with the service key from
  `.env`. **Never** in the app.
- Student progress refers to official items by stable IDs, so importing a new pack version
  never loses progress. Retired items are hidden, not deleted.

## 7. Core algorithms

### 7.1 Study day (`src/lib/time.ts`)
`studyDay(instant, tz = profile.timezone)` = the local date of `instant` in `tz`, minus one day
if the local time is before 03:00, as `YYYY-MM-DD`. (Reading the wall clock, rather than
subtracting 3 hours, keeps daylight-saving days right.)
All streak, XP-per-day and plan logic uses this.

### 7.2 Streak (`gamification/logic.ts`)
Input: the ordered study days with XP totals, plus `freezes_held` and repair history. Output:
`current`, `longest`, freezes consumed, `repair_available_until`. Rules are in PRODUCT_SPEC §8.2.
It is a pure function, tested with time-travel fixtures (missed day with/without freeze, repair
window, timezone edge at 02:59 vs 03:01).

### 7.3 Topic mastery (`mastery/logic.ts`) — initial formula, tunable
```
R  = mean FSRS retrievability now, over card instances linked to the topic that have been reviewed
A  = exponentially weighted accuracy over the last 30 question responses on the topic (half-life 10)
C  = coverage = (seen official cards + answered official questions) / (total official items in topic)
mastery = C × (0.6·R + 0.4·A)          (use R or A alone if the other has no data)
```
Levels: <20 Not started · <40 Learning · <60 Familiar · <85 Proficient · ≥85 Mastered.
It is recomputed after each session for the affected topics and nightly for all topics
(retrievability decays with time).

### 7.4 Roadmap unlocking
A node is available if the previous node in its section is completed, or its section is
unlocked and it is the first node. A section is unlocked if the previous section's checkpoint
has been passed (≥ 70 %) or the student passed this section's checkpoint as a "test-out". A
completed node becomes **needs review** when its topic's mastery is < 60.

### 7.5 Planner (`planner/logic.ts`)
Inputs: exam date, minutes per day, days off, remaining nodes with `est_minutes`, the FSRS
review forecast per day, and user-pinned items.
1. `days = study days from today to exam − 1`, excluding days off. `revisionDays = max(3,
   ceil(0.2 × days))`.
2. Capacity per day = minutes per day − forecast review minutes (≈ 8 s per review) − pinned
   items.
3. Fill the learning days greedily with remaining nodes in roadmap order. On revision days, add
   weak-spot drills and mocks.
4. If the capacity isn't enough, report the shortfall and suggest more minutes per day.
The plan regenerates on app open when the study day changes, or when inputs change. Items the
user has ticked are kept.

### 7.6 Quiz scoring (`quizzes/logic.ts`)
There is one scorer per question type: `score(question, response, settings) → {score, max,
isCorrect, detail}`. Every type has table-driven tests, including MTF negative marking,
numeric tolerance and fuzzy fill-in matching (normalised case, whitespace, Unicode Greek letters
such as "β" vs "beta").

## 8. Security & privacy
- RLS on every table. Add SQL tests in `supabase/tests/` proving user A can't read or write user B's rows.
- The anon key is the only key in the app. Edge Functions verify the JWT.
- No patient data. Profile fields are minimal. Supports data export and account deletion
  (an Edge Function deletes the rows and storage objects).
- Analytics are opt-out, with no content text sent — only event names and counts.
- Include the "for study only" disclaimer in onboarding, on drug profiles and in AI answers.

---

## 9. Performance budgets (low-end Android)
- Cold start to interactive Today screen: < 3 s on a ~3 GB RAM device.
- Review card flip and answer: < 100 ms response.
- APK (preview build) ideally < 40 MB. Content packs are ideally < 3 MB each (without images).
  Official images are downloaded per pack only when the user wants them.
- No list renders more than ~20 items without FlashList.

## 10. Testing strategy
- **Unit (Jest):** all `logic.ts` files — FSRS wrapper, queue builder, scorers, XP, streak,
  levels, achievements, mastery, planner, sync merge/replay, study-day, PK generator.
- **Repo tests:** Drizzle against an in-memory SQLite (better-sqlite3 in Jest) for key queries.
- **Component tests (RNTL):** question renderers, review card, streak widget.
- **E2E (Maestro):** onboarding · create note with image · create deck & review · build and
  take quiz · complete roadmap node (Phase 4).
- **RLS tests:** SQL scripts run against the Supabase project (Phase 3+).
